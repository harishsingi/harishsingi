              Same comparison, as a table: processing, efficiency and cost side by side.

              Before — calendar loads
              After — watermark loads
              Processing
              Glue → API, past-days fetch (the traditional way of using it): Glue connected straight to the Salesforce API and fetched a fixed window of past days of data. It never checked what the target already had, so anything outside that window was simply never picked up.
              →
              One fetch, 3 sub-steps inside the Glue downloader: ① Athena MAX(timestamp) gets the watermark, ② the per-table query is built from that watermark with a small overlap, ③ Salesforce is queried for only the changes since then.
              Efficiency
              High risk of missing data: if the job failed, or the API returned inconsistent / partial results, or records landed late for any other reason, that data was silently missed. The only reliable recovery was to perform a full load of everything.
              →
              Idempotent upserts make re-runs safe instead of duplicating data. After an outage the next run catches up by itself from the watermark — self-healing, no gaps, no full reloads — and PRE → SEM stays fast because it moves Iceberg to Iceberg.
              Cost
              Higher, and spiky: full loads and full reloads reprocess the entire dataset, so the work scales with the whole table instead of with what actually changed.
              →
              Lower, and steady: only the records changed since the watermark are processed, so the work scales with the change volume — and reload-sized recovery runs disappear.
              Missed changes: silent → noneRecovery: full reload → automatic catch-upReprocessing: whole table → changed records onlyRun cost: higher & spiky → lower & steady

              The base platform is the blueprint every project inherits — so wherever a source used to land on a calendar schedule, the same before / after applies.

              Before — calendar loads
              After — watermark loads
              Processing
              Calendar day-1 delta loads: each source's daily job fetched “yesterday”, on the assumption that yesterday's job actually ran.
              →
              Watermark run logic as the platform default: every load resumes from the target's last recorded timestamp, so catch-up is incremental and automatic for any source on the blueprint.
              Efficiency
              Full loads appended daily. A multi-day failure left silent gaps in the lake, and closing them meant reloading the full dataset before the downstream layers could be trusted again.
              →
              Layered, idempotent loads — raw, clean, then Gold on Iceberg. Re-runs are safe, missed windows refill themselves, and downstream layers read consistent snapshots: no gaps, no full reloads.
              Cost
              Higher: repeated full loads spend compute on records that never changed, and every recovery arrives as a reload-sized bill.
              →
              Lower: incremental-by-default means compute follows the volume of change, and Iceberg-to-Iceberg movement between layers keeps the heavy steps fast compared with full reprocessing.
              Schedule logic: calendar → watermarkMissed changes: silent → noneRecovery: full reload → automatic catch-upRun cost: higher → lower
              Before — polling batches
              After — continuous streaming
              Processing
              Polling batch jobs queried the source tables on a schedule and staged snapshots. Every consumer waited for the next batch, and analytic queries ran directly against the operational systems.
              →
              Publish once, consume many times: producers write events to Kafka topics; the stream processor (one collapsed node — consume & checkpoint, validate & enrich, window & sink, in the expandable panel above) handles events continuously as they arrive.
              Efficiency
              Coupled and lossy: a source schema change broke every downstream consumer at once, a missed poll meant missed changes, and with no replay there was no way to rebuild a consumer or recover an event after the fact.
              →
              Decoupled, with replay: producers and consumers evolve independently, each consumer reads at its own pace, and any consumer can replay the topic to catch up or rebuild — a new consumer starts from history, not from scratch.
              Cost
              Load in the wrong place: repeated full-table polls put analytic load on the operational databases, and freshness was bought with ever-more-frequent polling.
              →
              Load where it belongs: events are captured once and processed in the stream layer, so source systems are left alone and compute follows the actual event volume.
              Freshness: next batch → continuousRecovery: none → replayCoupling: every consumer breaks → independentSource load: repeated polls → captured once
              Before — Hive, copy to migrate
              After — Iceberg, converted in place
              Processing
              Full-copy migration: changing the table format — or even the partitioning — meant copying the entire dataset to a new location, pausing queries, and repointing every engine by hand.
              →
              Metadata conversion in place: the migration job (one collapsed node — inventory, convert in place, validate & cut over, in the expandable panel above) converts the table where it sits on the same S3 data. No data copy.
              Efficiency
              No safety net: Hive has no snapshots or ACID, so concurrent writers could overwrite each other, schema changes needed rewrites, and a bad load could not be rolled back — recovery meant restoring from backup.
              →
              Snapshots make mistakes cheap: every load is a snapshot, so a bad load rolls back in one step; schema and partition evolution happen without rewrites, and time-travel queries can audit or reproduce any earlier state.
              Cost
              Higher, and recurring: every format, schema or partition change re-billed as a full data copy plus downtime, and manual compaction and small-file cleanup never went away.
              →
              Lower, and mostly one-time: the conversion itself avoids the copy entirely, evolution stops triggering rewrites, and table maintenance becomes a managed, incremental job.
              Migration: full copy → in placeBad load: restore from backup → snapshot rollbackSchema change: rewrite → metadata onlyHistory: none → time travel
              Before — manual forecasts
              After — a loop, measured weekly
              Processing
              Manual extracts into spreadsheets and ad-hoc notebooks: features were rebuilt by hand every cycle, joins were not point-in-time correct, and the finished forecast lived in a slide or an email.
              →
              A repeatable pipeline: the feature → train → score loop (one collapsed node — point-in-time features, train & backtest, score & write back, in the expandable panel above) runs the same way every cycle, and forecasts land back in the lake as versioned data.
              Efficiency
              Unmeasured and person-dependent: with no versioned forecast there was nothing to compare actuals against, so accuracy was never really known — and the whole process depended on whoever built the spreadsheet.
              →
              Measured, not argued: every forecast version is scored against actuals, drift monitoring flags a decaying model early, and planners see predictions next to actuals in the same BI view everyone else uses.
              Cost
              Hidden cost: skilled time burned on manual extracts and rebuilds each cycle, plus the business cost of planning decisions taken on stale, unchecked numbers.
              →
              Effort shifts to decisions: the manual rebuild disappears, compute is spent on training and scoring rather than data wrangling, and planning works from fresher, checked forecasts.
              Forecast home: slides → versioned lake dataAccuracy: unknown → measured vs actualsFeatures: rebuilt by hand → repeatable pipelineModel decay: invisible → drift-monitored

              How to read the five patterns

              • Base platform: the blueprint every project inherits — land raw, validate, model, then serve.
              • CRM ingestion: Salesforce is just the example source. The SRC → PRE → SEM pattern works for any CRM.
              • Kafka streaming: a different shape entirely — events flow continuously, no daily batch to wait for.
              • Iceberg migration: Hive tables become Iceberg tables on the same S3 data, gaining snapshots and time travel.
              • ML forecasting: Gold data becomes features, features become a forecast, the forecast goes back to the business.
